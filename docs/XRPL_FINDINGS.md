# XRPL protocol findings from the build (devnet / testnet, 2026-10-24)

Facts we hit while building on the amendment-era primitives. Each one is backed by transaction metadata, preflight and RPC responses or device screens, recorded in `lending/EVIDENCE.md` or in testnet transaction metadata (every hash resolves at https://testnet.xrpl.org); finding 6 has no failure hash by nature, and finding 7 is a device screen.

1. **A `LoanSet` cannot be a Batch inner transaction.** rippled preflight returns `temINVALID_INNER_BATCH` ("Malformed: Invalid inner batch transaction.") for every variant we tried: broker→borrower (129B8292…), borrower→broker (0EBCD370…), with `CounterpartySignature` and a broker `BatchSigner` (61CB5138…), with `CounterpartySignature` and no `BatchSigner` (9D1656FD…). `VaultDeposit` is rejected the same way (46BE45EB…). Consequence: "loan + disbursement in one atomic step" is not expressible today. The working pattern is a co-signed `LoanSet` first (90B14608…), then an `AllOrNothing` Batch of plain Payments (35DF4112…, inners CEC27BB4…/3B49A298…). A Batch with an unpayable leg validates as `tesSUCCESS` on the outer transaction with no inner applied (2DCCD2D2…).
2. **Loan default cover math.** `CoverRateMinimum` and `CoverRateLiquidation` are in 1/100,000 units (100000 = 100%). The cover consumed on `LoanManage` default is `DebtTotal × CoverRateMinimum × CoverRateLiquidation`, so 10% × 10% = 1% of debt (A8DCC893… shows CoverAvailable 20,000,000 → 14,000,000 drops on a 60 XRP debt once liquidation was raised to 100000). With liquidation at 100% the cover hit on the 9/9 run's default (5777AFE3…) was 12,666,667 drops (CoverAvailable 20,000,000 → 7,333,333 = 10% of the 126,666,668-drop book) against a 60,000,000-drop default; the remaining 47,333,333 drops came out of the vault (AssetsTotal 180,000,003 → 132,666,670), so depositors' shares lost value. Cover + vault loss = default amount, exactly.
3. **Close-ended vault windows.** Before `SubscriptionDate`: `VaultDeposit` works, `LoanSet` = `tecTOO_SOON` (6589C5F6…). After it: `LoanSet` works (8EB1D3D3…), `VaultDeposit` = `tecEXPIRED` (3A703272…). `LoanBrokerSet` needs `VaultKind` = 1 (closed) under LendingProtocolV1_1.
4. **Loan objects live in the LoanBroker pseudo-account's owner directory** (and the borrower's), not the broker owner's. `account_objects` on the broker owner does not list them.
5. **A delegated Payment (`Delegate` field, PermissionDelegationV1_1) is refused by the T54 x402 facilitator** with `402 verify_failed:unsupported_payment_features`, so x402 payments must come from the signer's own account. Delegation works for direct payments: 203F666C… is a validated Payment with `Account` = treasury, `Delegate` = agent key, signed by the agent key.
6. **A delegated payment after a revoke returns `terNO_DELEGATE_PERMISSION` (-85) and never reaches the ledger.** There is no failure hash to show; the evidence is the submit response plus `account_objects type=delegate` returning `[]`. Because `ter` results are held by the receiving node until `LastLedgerSequence`, a re-grant inside that window could apply a "failed" delegated payment. Drills must use a short `LastLedgerSequence`.
7. **Ledger XRP app 2.8.1 does not decode `DelegateSet`'s permission field** and shows the granted permission as `Unknown [1]: 1` under blind signing (see `docs/LEDGER_DX_FEEDBACK.md` finding 11).
